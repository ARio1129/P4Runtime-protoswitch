# Tutorial 5：LPM × L2 リアルタイム通信可視化ツール

このツールは、`custom_topo.py`で構成した **P4スイッチs1、Linux L2ブリッジs2〜s4、ホストh1〜h12** の通信を可視化します。Mininetの`ping`を実行すると、実際に観測したICMP Echo Request / Replyをパケット型アイコン（REQ / REP）としてブラウザで動かします。**実通信はそのままの速度で記録し、ブラウザ側だけで低速再生**するので、速いpingの流れも1リンクずつ追えます。

## 使い方（macOS + Docker Desktop）

### 1. Tutorial 5のMininetとP4Runtime Shellを起動

チュートリアルのSTEP 02と同じコマンドでMininetを起動してください。Dockerコンテナ名は通常`p4mn-lpm-l2`です。**既存のDocker起動コマンドに`-p`などの追加設定は不要です。**

次に、STEP 03のP4Runtime Shellで以下4件のLPMエントリを登録してください。

| 宛先IPv4アドレス | s1の出力ポート | 接続先 |
|---|---:|---|
| `10.0.0.0/30` | 1 | s2（h1〜h3） |
| `10.0.0.4/30` | 2 | s3（h4〜h7） |
| `10.0.0.8/30` | 3 | s4（h8〜h11） |
| `10.0.0.12/30` | 4 | h12 |

### 2. Macの別のターミナルで可視化ツールを起動

このZIPを展開し、`lpm_l2_visualizer.py`と`dashboard.html`の入ったフォルダに移動して実行します。

```bash
python3 lpm_l2_visualizer.py
```

ブラウザが開かない場合は、以下を手動で開いてください。

`http://127.0.0.1:8766`

Mininetコンテナに接続できていれば、ステータスが**「Mininetのパケットを監視中（15 / 15 インターフェース）」**となります。

### 3. Mininetのターミナルでpingを実行

**STEP 04：異なるL2スイッチのホスト間**

```console
mininet> h1 ping -c 3 h5
```

通常、観測される経路は`h1 → s2 → s1 → s3 → h5`。Echo Replyは**h5が生成**し、`h5 → s3 → s1 → s2 → h1`の順に表示します。

**STEP 05：同じL2スイッチのホスト間**

```console
mininet> h1 ping -c 3 h2
```

初期表示は**全観測（分岐・返送も）**です。表示を「宛先へ向かう経路のみ」に切り替えると、観測できた場合の主経路は`h1 → s2 → h2`、応答は`h2 → s2 → h1`です。**s1はh2の代わりにICMP応答を作りません。** 未学習時にs2がフラッディングして、s1へもコピーが流れ、s1からs2に返送された場合は、画面の「表示する経路」を**全観測（分岐・返送も）**に切り替えると、それらのリンクを**主経路外**として表示します。学習済みかどうかをpingだけで断定することはできないため、Linux bridge FDBの取得結果も参照してください。

### 4. パケットの動きをゆっくり確認する（新機能）

画面上部の**パケット再生コントロール**を使います。

| 操作 | 内容 |
|---|---|
| **再生速度** | `0.1× / 0.25× / 0.5× / 1× / 1.5× / 2× / 4×`。初期値は `0.5×`。最も遅い `0.1×` なら1リンク約12.5秒かけて移動します。 |
| **一時停止 / 再生** | アイコンの移動を途中で止めて、その位置から再開できます。**停止中もパケットの観測と記録は継続**します。 |
| **1リンク進める** | ボタンを押すごとに、記録された次のリンク1本をパケットが移動し、その後に停止します。 |
| **最初から再生** | 観測済みの履歴を先頭からもう一度再生します。pingコマンドの再実行は不要です。 |
| **最新のpingを見る** | 長い低速再生の途中でも、古いキューを飛ばして直近のICMPシーケンス番号のリンクから再生します。 |
| **各pingの観測結果** | ICMP ID・シーケンス番号ごとのREQ/REPが観測されたリンク件数（送信回数ではない）、返信が送信元側リンクまで到達したか、分岐が観測されたかを表示します。再生速度とは独立して即時更新します。 |
| **表示する経路** | 「宛先へ向かう経路のみ」（切替可）／「全観測（分岐・返送も）」（初期値）を切り替える。前者では各ICMP要求・応答につき同じリンクの再観測をまとめ、後者では「本来の宛先以外にも転送されたパケットの経路」を灰色の破線で示し、同じリンクの再観測も表示します。切り替えても観測履歴は消えません。 |
| **通信フィルター** | h1↔h5またはh1↔h2だけを絞り込んで、保存した観測履歴から再生します。 |
| **通信をクリア** | 上部の再生操作欄から、パケットの観測履歴と画面のログを消去して、次のpingを待機します。MininetのMAC学習やP4エントリは変更しません。 |

おすすめの確認方法：Mininetで **`h1 ping -c 1 h5`** を一度だけ実行 → ブラウザで一時停止 → `1リンク進める`を繰り返す。チュートリアルと同じ3回の通信を見たい場合は、`h1 ping -c 3 h5`を実行します。

再生中のパケット型アイコンには、要求を表す `REQ` と応答を表す `REP`、およびICMPのシーケンス番号を表示します。画面の「今のパケット」には**送信元・転送先ノード・観測インターフェース・宛先IP**を表示します。

**注意：** 各リンク上のパケットの移動は、観測した通過イベントを見やすい時間軸で描画したものです。リアルタイムの伝送速度・実際の伝送遅延の再現ではありません。pingの応答が返らなかった場合、届いていない経路を自動で補完することもありません。

### 5. 終了

可視化ツールのターミナルで`Ctrl+C`を押してください。MininetとP4Runtime Shellは独立しているので、必要なときにそれぞれ終了できます。

## オプション

```bash
# Dockerなしで画面の動きを試す（架空の通信を明示）
python3 lpm_l2_visualizer.py --demo

# コンテナ名が異なる場合

# ブラウザ用ポートを変更する場合
python3 lpm_l2_visualizer.py --port 8877

# ブラウザの自動起動を止める場合
python3 lpm_l2_visualizer.py --no-browser
```

## 仕組みと制限

- Macから`docker exec`を使い、実行中のMininetコンテナ内でPython標準ライブラリの`AF_PACKET`によってEthernetフレームを観測します。`tcpdump`のインストールも`pip install`も不要です。ただし**コンテナ内でPython 3が使用でき、root権限でRaw Socketを開けること**が必要です。Tutorial 5の`--privileged`コンテナを想定しています。
- **スイッチ側15インターフェース（各リンクにつき一方だけ）**を監視します。例えばs1–s2の間は`s1-eth1`を観測します。ホスト側ネットワーク名前空間に直接入る必要はありません。
- リンク上の**ICMP Echo Request / Reply**をICMP識別番号・シーケンス番号・通信相手でまとめ、短い観測待ち時間（約0.65秒）の後に再生します。各観測を「送信元から宛先へのトポロジー上の最短経路」と「主経路外のコピー」に分類します。これは**経路上の観測リンクを見やすくするための分類**であり、パケットが本当に通ったかをトポロジーだけから推測して描画するものではありません。
- コンテナ内Linuxで`SO_TIMESTAMPNS`が利用可能なときは**カーネルが記録したパケット時刻**で観測を並べ、h1→s2→s1→s2のような往復を含む経路でも順序を保ちます。利用できないときは、主経路を先に並べた教材用の表示順とし、画面にその旨を示します。いずれもアニメーション速度は現実の伝送速度とは異なります。
- **未観測リンクを描画で補完することはありません。** 例えばh5→s3が記録されず、最初にs3→s1が観測された場合、返信元はh5と明示し「送信元からの最初のリンクは観測できませんでした」と表示します。フラッディングなど分岐がある場合、同じ深さのリンク順は実時刻の厳密な再現ではありません。
- P4のLPMエントリ表はTutorial 5の設定に基づく**参考情報**です。実際にP4Runtimeからエントリを読み取って同期する機能ではありません。内部のテーブルヒットを直接取得するものではありません。
- LinuxブリッジのMAC学習状況は、コンテナに`bridge`コマンドがある場合、`bridge fdb show br s2`等の**実測結果**を表示します。取得できない場合は「対応していない環境」と表示します。
- 画面はMacの`127.0.0.1:8766`で配信され、外部ネットワークに公開されません。
- Mininet/Dockerに対する設定変更や、新しいP4テーブルエントリの登録は行いません。**可視化のみ**です。
- 本環境ではユーザーのDocker Desktop/Mininetコンテナを実際に起動しての接続検証は行っていません。ローカルのデモ、Python構文、HTTP配信、パケット解析のテストを行っています。

## 同じL2スイッチ内の通信が不自然に見えた場合

1. Mininetで`h1 ping -c 1 h2`を実行します。
2. 可視化画面の通信フィルターを「h1 ↔ h2」、表示する経路を**「宛先へ向かう経路のみ」**にします。
3. `h1 → s2 → h2`（要求）と`h2 → s2 → h1`（応答）のうち、**実際に観測できたリンクだけ**が表示されます。s1は主経路に含まれません。
4. **「全観測（分岐・返送も）」**へ切り替えると、学習前のフラッディングでs2→s1やs2→h3のコピーが観測されていれば表示されます。s1→s2の返送が観測された場合も表示されます。
5. 観測されないリンクは描画しません。主経路と全観測の両方で予期しない経路になった場合は、スクリーンショットと観測ログを比較してください。

**注：** 同じL2内の「主経路」はトポロジー上の宛先に向かう経路を意味し、必ず全フレームがそこだけを通るという意味ではありません。フラッディング中に同一パケットのコピーが複数リンクで観測されるのは正常に起こり得ます。Linuxのブリッジの学習状態やP4側の返送により、同じリンク上に複数のコピーが観測される場合があります。

## 返信が表示されない・s1やh3に送られない場合

- 今回の改良では、**「全観測（分岐・返送も）」が初期設定**です。s2がh2の宛先MACアドレスを未学習の場合に限り、s2→s1やs2→h3などのコピーが観測されることがあります。既に学習済みの場合は、これらのコピーが流れないことが正常です。フラッディングを強制表示することはありません。
- ブラウザの**「各pingの観測結果」**はパケットを記録した時点で更新されます。遅いアニメーションがまだ1回目の通信を再生していても、2回目・3回目のREQとREPが観測できたかを確認できます。
- **「最新のpingを見る」**で古い再生待ちを飛ばして直近の通信を再生できます。必要に応じて表示速度を上げてください。
- **`REP 未観測`**と表示されたときは、可視化ツールに応答が記録されていないことを意味します。実通信の失敗とは限りません。まずMininetで`h1 ping -c 3 h2`を実行し、`packets transmitted/received`を確認してください。
- Mininet自体もパケットを失っているなら、LinuxブリッジのFDBを点検してください（例：`mininet> s2 bridge fdb show br s2`）。このツールはP4プログラムやMAC学習テーブルを変更せず、通信障害を自動で修復するものではありません。
- パケット監視ワーカーはLinuxブリッジのFDB取得を別スレッドで行い、キャプチャが滞らないように修正しました。ただし、MacのDocker環境での実動作は未検証です。

## 実機で問題が続くときの診断（重要）

このプログラムの開発環境ではDocker/Mininetを起動できないため、ブラウザ・サーバー・合成パケットの結合テストと、**Mac上の実通信テストは別物**です。実通信で問題が続く場合は、pingの結果を確かめてください。

1. Mininetで`h1 ping -c 3 h2`を実行し、`3 packets transmitted, ... received`を記録します。
2. 可視化画面で「診断ログを保存」をクリックすると、**画面に補完していない生のICMP観測データ**を`icmp_diagnostics.json`に保存できます。
3. ファイルには、観測時刻・取り込んだ時刻・ICMP種別・識別番号・seq・インターフェース・方向・MACアドレスと、取得時点のLinuxブリッジFDBが入ります。ご自身のネットワーク情報を含むため、共有する前に内容を確認してください。
4. FDBの表示で、例えばh1のMACが`s2-eth1`（本来`s2-eth2`）に学習されていれば、P4スイッチs1が同じポートへ送り返したフレームによる誤学習の可能性があります。**これは可視化の不具合ではなく実験用ネットワーク側の問題**なので、可視化ツールだけでは解決できません。

**検証の境界：** 単体テストや合成パケットを使ったブラウザ結合テストが成功しても、実際のMacのDocker/Mininetで3回の返信が到達することは保証しません。

### 開発時の確認手順

標準ライブラリの17件以上の単体テストは次で実行できます。

```bash
python3 -m unittest discover -s . -p 'test_lpm_l2_visualizer.py' -v
```

また、開発時に「偽のDockerイベントストリーム→Pythonの取り込みとグループ化→HTTP診断出力→Chromiumでの描画」という結合テストを行っています。これは実際のMininetを用いた通信試験とは**別の検証**です。
